# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

## 1. 실행 환경 및 실행 방법

- 실행할 때마다 `srand(time(NULL))`로 새로운 무작위 데이터를 만들기 때문에 비교 횟수는 실행마다 조금씩 달라진다. 그래서 프로그램을 3번 실행하고 결과를 비교했다.
- 실행시간 측정에는 C11 표준 함수인 `timespec_get()`을 사용했다.

## 2. 구현 내용

### 2.1 데이터 생성
- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 각 크기마다 0 ~ 99,999 범위의 무작위 정수를 만들었고, 중복 값도 허용했다.
- 세 가지 피벗 방법은 `memcpy()`로 같은 원본 배열을 복사해서 사용했다. 따라서 세 방법은 완전히 같은 데이터를 정렬한다.

### 2.2 피벗 선택 방법
세 방법 모두 **피벗을 고르는 부분만 다르고**, 고른 피벗을 구간의 첫 번째 칸으로 옮긴 다음 **같은 분할 함수(`partition`)** 를 사용하도록 구현했다.

| 방법 | 피벗 |
|---|---|
| First | 현재 구간의 첫 번째 원소 |
| Random | 현재 구간에서 무작위 위치의 원소 (분할할 때마다 새로 선택) |
| Median-of-Three | 첫 번째, 가운데, 마지막 원소 중 크기가 가운데인 값 |

### 2.3 분할 방법
- 피벗을 `list[left]`에 둔다.
- `low`는 왼쪽에서 오른쪽으로 이동하면서 피벗보다 작지 않은 값을 찾는다.
- `high`는 오른쪽에서 왼쪽으로 이동하면서 피벗보다 크지 않은 값을 찾는다.
- 두 값을 교환하고, `low`와 `high`가 엇갈리면 피벗을 `high` 위치로 옮긴다. 이 위치가 피벗의 최종 자리다.

### 2.4 비교 횟수를 세는 기준
- 데이터 값끼리 비교할 때는 `LESS()`, `GREATER()` 함수만 사용하게 했고, 이 함수가 호출될 때마다 `cmp_count`를 1씩 늘렸다.
- 분할 과정에서 데이터 값과 피벗 값을 비교한 횟수를 셌다.
- Median-of-Three에서 중앙값을 정하려고 비교한 횟수(분할마다 2~3회)도 포함했다.
- 반복문의 인덱스 비교(`low <= right` 등), 무작위 위치 생성, 데이터 이동(교환)은 포함하지 않았다.
- 정렬이 끝나면 `is_sorted()`로 오름차순 정렬이 맞는지 확인했다. 이 확인 과정의 비교는 비교 횟수에 넣지 않았다. 3번 실행 모두 정렬 오류는 없었다.

## 4. 분석

### 4.1 데이터 크기 증가에 따른 비교 횟수 변화
n이 2배가 될 때 비교 횟수가 몇 배가 되는지 3회 평균(Median-3)으로 계산했다.

| n 변화 | 비교 횟수 증가 | n log₂n 증가 |
|---|---:|---:|
| 1,000 → 2,000 | 2.16배 | 2.20배 |
| 2,000 → 4,000 | 2.17배 | 2.18배 |
| 4,000 → 8,000 | 2.12배 | 2.17배 |
| 8,000 → 16,000 | 2.23배 | 2.15배 |

세 방법 모두 n이 2배가 되면 비교 횟수가 2배보다 조금 더 많은 약 2.1~2.2배로 늘었다. 이 값은 n log₂n의 증가 비율과 거의 같다. 만약 O(n²)이었다면 4배씩 늘어났을 것이다. 따라서 무작위 데이터에서는 세 방법 모두 퀵 정렬의 평균 시간 복잡도인 **O(n log n)** 으로 동작했다는 것을 확인했다.

비교 횟수를 n log₂n으로 나눠 보면 First는 약 1.21~1.26, Random은 약 1.20~1.29, Median-3는 약 1.16~1.21로 크기와 상관없이 거의 일정했다. 즉, 비교 횟수는 n log₂n에 일정한 상수를 곱한 정도로 늘어나고, Median-3는 그 상수가 가장 작았다.

### 4.2 피벗 선택 방법에 따른 성능 차이

**First와 Random이 비슷한 이유**
이번 실험의 데이터는 무작위로 만들었기 때문에, 구간의 첫 번째 원소도 사실상 무작위로 뽑은 값과 같다. 그래서 First와 Random은 피벗이 구간에서 몇 번째 크기의 값이 될지에 대한 확률이 같고, 비교 횟수도 비슷하게 나왔다. 실제로 3회 평균에서 n = 8,000과 20,000에서는 Random이 조금 적었고, 나머지 크기에서는 First가 조금 적어서 일정한 우열이 없었다.

**Median-3가 가장 적은 이유**
퀵 정렬은 피벗이 구간을 **반반으로 나눌수록** 빠르다. 피벗이 너무 작거나 크면 한쪽 구간만 길게 남아서 분할 단계 수가 늘어나고, 그만큼 비교도 늘어난다.

- First, Random: 값 하나를 뽑기 때문에, 구간에서 가장 작은 값이나 가장 큰 값 근처가 뽑힐 확률이 꽤 있다.
- Median-3: 값 세 개 중 가운데 값을 쓰기 때문에, 가장 작은 값이나 가장 큰 값이 피벗이 되려면 세 값이 모두 한쪽 끝에 몰려야 한다. 그래서 피벗이 구간의 가운데 크기에 더 가까워지고, 분할이 더 고르게 된다.

Median-3는 분할할 때마다 중앙값을 구하는 비교가 2~3번 더 들어간다. 그런데 분할이 고르게 되어 줄어드는 비교 수가 더 많아서, n = 2,000 이상에서는 First보다 약 3~8%, Random보다 약 4~8% 비교 횟수가 적었다. n = 1,000에서는 차이가 거의 없었는데, 데이터가 적으면 분할 단계 자체가 적어서 고른 분할로 얻는 이득이 중앙값을 구하는 추가 비교와 비슷해지기 때문이라고 생각했다. 실제로 가장 큰 n = 20,000에서 First 대비 7.5%로 감소율이 컸다.

**데이터가 정렬되어 있었다면** (이론적인 분석)
이번 실험은 무작위 데이터만 사용했기 때문에 First의 약점이 드러나지 않았다. 하지만 이미 정렬된 데이터에서 First를 쓰면, 매번 구간의 가장 작은 값이 피벗이 된다. 그러면 구간이 1칸씩만 줄어들어서 O(n²)이 된다. 반면 Random은 데이터 순서와 상관없이 무작위로 뽑으니 이런 상황을 피할 수 있고, Median-3는 정렬된 데이터에서 가운데 원소를 고르게 되어 오히려 가장 이상적인 피벗이 된다.

### 4.3 가장 효과적인 피벗 선택 방법
실험 결과로는 **Median-of-Three가 가장 효과적이었다.** 3회 평균에서 n = 2,000 이상의 모든 크기에서 비교 횟수가 가장 적었고, 비교 횟수를 n log₂n으로 나눈 값도 가장 작았다. 또한 데이터가 이미 정렬된 경우에도 피벗을 잘 고를 수 있기 때문에, 실제로 사용하기에도 가장 안정적인 방법이라고 판단했다.

## 5. [보너스] 재귀적 퀵 정렬과 반복적 퀵 정렬

### 5.1 구현
- 재귀: `quick_sort_recursive()`가 피벗의 왼쪽 구간과 오른쪽 구간에 대해 자기 자신을 다시 호출한다.
- 반복: `quick_sort_iterative()`가 정렬할 구간 `(left, right)`를 직접 만든 배열 스택에 넣고 꺼내면서 정렬한다. 두 구간 중 큰 구간을 먼저 넣어서 작은 구간부터 처리하게 했다. 이렇게 하면 스택에 쌓이는 구간 수가 줄어든다.
- 두 방법 모두 Median-of-Three 피벗과 같은 `partition()` 함수를 사용했다.
- n = 10,000인 같은 원본 데이터를 100번 정렬해서 평균 실행시간을 구했다. 배열 복사와 정렬 확인은 측정 구간 밖에서 했다.

### 5.2 결과

| 회차 | Recursive | Iterative | 반복 / 재귀 |
|:---:|---:|---:|---:|
| 1 | 3.7704 ms | 4.4111 ms | 1.17배 |
| 2 | 1.8591 ms | 1.9586 ms | 1.05배 |
| 3 | 2.2911 ms | 2.3952 ms | 1.05배 |
| 평균 | 2.6402 ms | 2.9216 ms | 1.11배 |

### 5.3 분석
3번 모두 **재귀적 방법이 조금 더 빨랐다.** 2회차와 3회차는 반복적 방법이 약 5% 느렸고, 1회차는 약 17% 느렸다.

- **실행마다 시간이 다른 이유**: 1회차는 두 방법 모두 2회차, 3회차보다 시간이 많이 걸렸다. 정렬 작업량은 매번 같기 때문에, 실행 시점의 CPU 상태나 다른 프로그램의 영향 같은 실행 환경 차이 때문이라고 생각했다. 그래서 절대적인 시간보다는 같은 실행 안에서 두 방법의 비율을 비교하는 것이 더 정확하다고 판단했다.
- **차이가 크지 않은 이유**: 두 방법은 같은 피벗과 같은 분할 함수를 쓰기 때문에, 시간이 가장 많이 걸리는 비교와 교환 작업은 완전히 같다. 다른 점은 "다음에 정렬할 구간을 어디에 기억하느냐"뿐이다. 재귀는 함수 호출 스택에, 반복은 직접 만든 배열 스택에 기억한다.
- **반복이 조금 느린 이유**: 반복적 방법은 정렬할 때마다 스택 배열을 `malloc()`으로 할당하고 `free()`로 해제한다. 또 구간 하나마다 `left`, `right` 두 값을 직접 배열에 넣고 빼야 한다. 반면 재귀 호출은 CPU가 제공하는 함수 호출 스택을 사용해서 빠르게 처리되고, 피벗이 고르게 나뉘면 재귀 깊이도 약 log₂n(n = 10,000일 때 약 14) 정도라서 호출 비용이 크지 않다.
- **반복적 방법의 장점**: 이번 실험에서는 속도 이점이 없었다. 하지만 피벗이 계속 한쪽 끝으로 뽑히는 최악의 경우에는 재귀 깊이가 n까지 깊어져서 스택 오버플로가 날 수 있다. 반복적 방법은 작은 구간부터 처리하도록 구현했기 때문에 스택 사용량이 log n 수준으로 유지되어 이런 문제를 피할 수 있다.
