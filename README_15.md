# 과제 15: 퀵 정렬과 AVL 트리 정렬의 성능 비교

## 1. 실행 환경 및 실행 방법

- 컴파일 및 실행
./sort15

- 실행할 때마다 `srand(time(NULL))`로 새로운 데이터와 연산 순서를 만들기 때문에 결과는 실행마다 조금씩 달라진다.

## 2. 구현 내용

### 2.1 데이터와 연산 생성
- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 이전 과제와 같은 방법으로 0 ~ 99,999 범위의 무작위 정수를 만들었고, 중복 값도 허용했다.
- 삽입·삭제 연산은 n의 20%만큼 수행했다(200 / 400 / 800 / 1,600 / 3,200 / 4,000회).
- 연산마다 난수를 하나 만들어 짝수면 삽입, 홀수면 삭제로 정했고, 실제로 삽입·삭제할 값은 새 난수(0 ~ 99,999)로 따로 만들었다.
- 데이터와 연산 목록(연산 종류, 값)을 측정 전에 미리 만들어 두고, 배열과 AVL 트리에 **같은 데이터, 같은 순서, 같은 값**을 적용했다. 그래서 난수 생성 시간은 측정에 들어가지 않는다.

### 2.2 배열 + 퀵 정렬
- 정렬: 과제 12~14에서 구현한 퀵 정렬을 사용했다. 피벗 선택 방법은 이전 과제들에서 비교 횟수와 재귀 깊이가 가장 적었던 **Median-of-Three**(첫 번째, 가운데, 마지막 원소의 중앙값)를 사용했다.
- 삽입(`array_insert`): 배열 앞에서부터 선형 탐색으로 삽입할 값보다 큰 값이 처음 나오는 위치를 찾는다. 그 위치부터 끝까지의 값을 뒤에서부터 한 칸씩 뒤로 옮기고, 빈 자리에 새 값을 넣는다. 같은 값이 있으면 그 뒤에 넣는다.
- 삭제(`array_delete`): 배열 앞에서부터 선형 탐색으로 삭제할 값을 찾는다. 배열이 정렬되어 있으므로 삭제할 값보다 큰 값이 나오면 값이 없다고 판단하고 멈춘다. 찾으면 그 뒤의 값을 한 칸씩 앞으로 옮긴다.
- 배열은 삽입에 대비해 `n + 연산 횟수` 크기로 할당했다.

### 2.3 AVL 트리
- 정렬: 같은 원본 데이터를 처음부터 하나씩 AVL 트리에 삽입했다. 삽입할 때마다 균형이 깨지면 회전으로 복구하므로 트리는 항상 정렬 상태와 균형을 유지한다.
- 노드 구조: 값(`key`), 같은 값의 개수(`count`), 높이(`height`), 왼쪽·오른쪽 자식 포인터
- **중복 값**: 같은 값이 들어오면 새 노드를 만들지 않고 `count`만 1 늘렸다. 삭제할 때도 `count`가 2 이상이면 1만 줄여서, 해당 값의 원소 하나만 제거했다.
- 삽입·삭제 후 높이를 다시 계산하고, 균형 인수(왼쪽 높이 − 오른쪽 높이)가 2 이상이거나 −2 이하이면 LL, LR, RR, RL 회전으로 균형을 복구했다.
- 자식이 2개인 노드를 삭제할 때는 오른쪽 서브트리의 최솟값(후계자)의 값과 개수를 복사해 오고, 후계자 노드를 떼어냈다.

### 2.4 결과 확인
- 정렬 직후: 배열이 오름차순인지 확인하고, AVL 트리를 **중위 순회**한 결과(중복 값은 `count`만큼 반복)가 퀵 정렬 결과와 완전히 같은지 비교했다.
- 모든 연산 후: AVL 트리의 중위 순회 결과와 배열을 원소 하나하나 비교해서 데이터 구성이 같은지 확인했다.
- 모든 크기에서 두 확인을 통과했고, 최종 데이터 개수도 같았다.

## 3. 측정 방법

### 3.1 총 수행시간
- **총 수행시간 = 정렬 시간 + 삽입·삭제 시간**
- C11 표준 함수 `timespec_get()`으로 정렬 시작과 끝, 삽입·삭제 시작과 끝의 시간을 쟀다.
- 정렬과 삽입·삭제 사이의 결과 확인, 배열 복사, 난수 생성, 출력, 트리 메모리 해제는 측정 구간 밖에서 했다.
- 시간이 짧아서 같은 과정을 10번 반복하고 평균을 냈다.

### 3.2 비교 횟수
- 데이터 값끼리 비교할 때는 `LESS()`, `GREATER()`, `LESS_EQUAL()`, `EQUAL()` 함수만 사용했고, 호출될 때마다 1씩 셌다.
- 포함: 퀵 정렬의 분할과 피벗 선택, 배열의 삽입 위치 탐색과 삭제 대상 탐색, AVL 트리에서 값을 넣을 위치와 삭제할 값을 찾는 비교
- 제외: AVL의 높이 비교와 균형 인수 계산, 인덱스 비교, NULL 검사 같은 데이터 값과 무관한 비교

### 3.3 데이터 이동 횟수
데이터 값을 복사하거나 대입할 때만 셌다.

| 동작 | 이동 횟수 |
|---|---|
| 퀵 정렬 교환(swap) | 3회 (`t = a`, `a = b`, `b = t`) |
| 퀵 정렬 피벗 값 저장 | 1회 |
| 배열 삽입·삭제에서 값을 한 칸 옮김 | 1칸당 1회 |
| 배열에 새 값 저장 | 1회 |
| AVL 새 노드에 값 저장 | 1회 |
| AVL 삭제 시 후계자 값 복사 | 1회 |

AVL의 회전(포인터 연결 변경)과 `count` 증감은 데이터 값의 이동이 아니므로 제외했다.

### 3.4 메모리 사용량
**최대 메모리 = 자료구조 크기 + 최대 스택 사용량**

- **배열**: 정렬과 삽입·삭제 중 원소가 가장 많았을 때의 개수 × `sizeof(int)`(4바이트)
- **AVL 트리**: 정렬과 삽입·삭제 중 노드가 가장 많았을 때의 개수 × `sizeof(AVLNode)`(32바이트)
  - 노드 하나 = `key` 4 + `count` 4 + `height` 4 + 정렬용 빈 공간 4 + 포인터 2개 16 = 32바이트
  - `malloc()` 자체가 내부적으로 쓰는 관리용 공간은 운영체제마다 달라서 포함하지 않았다.
- **스택**: 과제 13, 14와 같은 방법으로, 측정 함수의 지역 변수 주소와 정렬·삽입·삭제 중 가장 깊이 내려간 함수의 지역 변수 주소의 차이를 쟀다. 퀵 정렬의 재귀, AVL 삽입·삭제의 재귀, 회전 함수가 모두 포함된다.
- 이번 과제는 "자료구조를 포함한 메모리"를 비교하기 때문에, 이전 과제와 달리 데이터를 저장하는 배열과 트리 자체의 크기도 포함했다.

비교 횟수, 이동 횟수, 메모리는 첫 번째 실행에서 측정했고, 시간은 측정용 기록을 끈 상태로 10번 반복해서 측정했다.

## 5. 분석

### 5.1 총 수행시간과 비교 횟수 차이

**정렬 단계만 보면 두 방법은 비슷했다.**
n = 20,000에서 정렬 단계의 비교 횟수는 퀵 정렬 334,068, AVL 387,843으로 AVL이 약 16% 더 많았다. n log₂n으로 나누면 퀵 정렬은 약 1.15 ~ 1.22, AVL은 약 1.31 ~ 1.36으로, 둘 다 O(n log n)이다. AVL은 값 하나를 넣을 때 루트에서 리프까지 트리 높이만큼 내려가는데, 내려갈 때마다 "작은가"와 "큰가"를 차례로 비교해서 한 단계에 최대 2번 비교하기 때문에 조금 더 많았다.

**차이는 삽입·삭제 단계에서 생겼다.**
연산 한 번당 비교 횟수를 계산하면 차이가 분명하다.

| n | 배열 (연산 1회당 비교) | AVL (연산 1회당 비교) |
|---:|---:|---:|
| 1,000 | 528 | 15.5 |
| 4,000 | 2,138 | 18.5 |
| 20,000 | 10,438 | 21.4 |

- **배열**: 삽입 위치나 삭제할 값을 앞에서부터 하나씩 비교하며 찾는다. 찾는 값은 평균적으로 배열의 중간쯤에 있으므로 연산 1번에 약 n/2번 비교한다. 실제로 n = 20,000에서 10,438번으로 n/2와 거의 같았다. 즉 연산 1번이 **O(n)** 이다.
- **AVL**: 루트에서 시작해 값이 작으면 왼쪽, 크면 오른쪽으로 내려가므로, 트리 높이만큼만 비교한다. AVL 트리는 회전으로 높이를 약 log₂n으로 유지한다(n = 20,000에서 높이 17, log₂n ≈ 14.3). 그래서 연산 1번이 **O(log n)** 이고, n이 20배가 되는 동안 연산 1번당 비교 횟수는 15.5에서 21.4로 1.4배만 늘었다.

그 결과 전체 비교 횟수에서 삽입·삭제가 차지하는 비율이 배열은 n = 1,000에서 약 90%, n = 20,000에서 약 99%였다. 연산이 n의 20%밖에 되지 않는데도, 배열은 정렬보다 삽입·삭제에 훨씬 많은 비교를 했다. n = 20,000에서 전체 비교 횟수는 배열이 AVL의 약 89배였다.

**총 수행시간도 같은 경향을 보였다.**
퀵 정렬(배열)의 수행시간은 AVL의 1.8배(n = 1,000)에서 20.7배(n = 20,000)로, n이 커질수록 차이가 크게 벌어졌다. 비교와 이동 횟수의 차이가 그대로 시간 차이로 나타났다.

다만 비교 횟수의 차이(89배)보다 시간 차이(20.7배)가 작았다. 배열은 연속된 메모리를 앞에서부터 차례로 읽기 때문에 CPU 캐시를 잘 활용해서 비교 1번이 빠르다. 반면 AVL은 노드가 메모리 여기저기에 흩어져 있어서 포인터를 따라갈 때마다 다른 위치를 읽어야 하고, `malloc()`으로 노드를 만드는 비용과 높이 갱신, 회전 비용도 든다.

### 5.2 삽입·삭제 과정의 데이터 이동 횟수 차이

| n | 배열 (연산 1회당 이동) | AVL (연산 1회당 이동) |
|---:|---:|---:|
| 1,000 | 344 | 0.61 |
| 4,000 | 998 | 0.47 |
| 20,000 | 6,302 | 0.45 |

- **배열**: 배열은 원소가 메모리에 연속으로 붙어 있어야 한다. 그래서 중간에 값을 넣으려면 그 뒤의 값을 전부 한 칸씩 뒤로 밀고, 값을 빼면 그 뒤의 값을 전부 한 칸씩 앞으로 당겨야 한다. 연산 1번에 평균 수백 ~ 수천 번의 이동이 생겼고, n에 비례해서 늘었다. n = 20,000에서 삽입·삭제 단계의 이동은 25,206,670회였다.
- **AVL**: 노드는 포인터로 연결되어 있어서, 값을 넣거나 빼도 다른 노드의 값을 옮기지 않는다. 새 노드를 만들 때 값을 1번 저장하고, 자식이 2개인 노드를 삭제할 때 후계자 값을 1번 복사하는 것이 전부다. 균형을 맞추는 회전도 포인터만 바꾸므로 이동 횟수에 들어가지 않는다. 그래서 연산 1번당 이동이 1회도 되지 않았다.
- AVL에서 연산 1번당 이동이 1보다 작은 이유는, 이미 있는 값을 삽입하면 `count`만 늘리고, 삭제가 실패하면 아무것도 옮기지 않기 때문이다.

또 정렬 단계에서도 이동 횟수가 크게 달랐다(n = 20,000에서 퀵 정렬 237,233회, AVL 18,105회). 퀵 정렬은 분할할 때마다 교환(3회 이동)을 반복하지만, AVL은 서로 다른 값마다 노드를 하나 만들 때 1번만 저장하기 때문이다. AVL 정렬 단계의 이동 횟수가 n보다 조금 작은 것도 중복 값은 새 노드를 만들지 않기 때문이다.

### 5.3 배열과 AVL 트리의 메모리 사용량 차이

**메모리는 AVL 트리가 배열의 약 6.6 ~ 7.4배였다.**
n = 20,000에서 배열은 88,292B, AVL은 623,204B였다.

| | 데이터 1개를 저장하는 데 필요한 공간 |
|---|---|
| 배열 | `int` 1칸 = 4바이트 |
| AVL 노드 | 값 4 + 개수 4 + 높이 4 + 빈 공간 4 + 포인터 2개 16 = 32바이트 |

- AVL 노드는 값 하나를 저장하려고 포인터 2개(16바이트)와 높이, 개수까지 함께 저장한다. 그래서 값 1개당 공간이 배열의 8배다.
- 실제 비율이 8배보다 조금 작은 이유는 중복 값이 노드 하나를 같이 쓰기 때문이다. n = 20,000에서 최종 데이터는 21,644개인데 최대 노드 수는 19,420개였다. 데이터가 많을수록 중복 값이 많아져서, 데이터 1개당 AVL 메모리는 n = 1,000에서 약 33.0바이트, n = 20,000에서 약 28.8바이트로 줄었다.
- 스택은 두 방법 모두 약 1.1 ~ 1.8KB로 비슷했다. 퀵 정렬의 재귀 깊이와 AVL의 재귀 깊이(트리 높이)가 모두 약 log n 수준이기 때문이다. 그래서 전체 메모리 차이는 거의 다 자료구조 자체의 크기 차이에서 나왔다.
- `malloc()`의 내부 관리 공간까지 생각하면, 실제 AVL 트리의 메모리는 측정값보다 더 클 수 있다.

### 5.4 데이터 크기 증가에 따른 성능 변화

n이 2배가 될 때 증가 비율을 계산했다.

| n 변화 | 배열 비교 | AVL 비교 | 배열 이동 | AVL 이동 |
|---|---:|---:|---:|---:|
| 1,000 → 2,000 | 4.00배 | 2.19배 | 2.91배 | 1.94배 |
| 2,000 → 4,000 | 3.76배 | 2.24배 | 3.72배 | 1.97배 |
| 4,000 → 8,000 | 3.89배 | 2.16배 | 4.41배 | 1.97배 |
| 8,000 → 16,000 | 3.91배 | 2.15배 | 4.25배 | 1.92배 |

- **배열은 n이 2배가 되면 비교와 이동이 약 4배**로 늘었다. 연산 횟수가 n의 20%로 n에 비례하고, 연산 1번의 비용도 n에 비례하므로 전체는 **n²** 에 비례한다.
- **AVL은 비교가 약 2.2배**로 늘어서 n log₂n의 증가 비율(약 2.15 ~ 2.2배)과 거의 같았다. 정렬과 삽입·삭제 모두 값 하나당 O(log n)이므로 전체가 **O(n log n)** 이다. 이동은 약 2배로 n에 비례했다.
- **수행시간**도 배열은 n = 1,000에서 20,000으로 20배가 될 때 약 186배(0.7992 → 148.3722 ms)로 늘었고, AVL은 약 16배(0.4410 → 7.1761 ms)로 늘었다.
- 단, n = 8,000의 수행시간은 다른 크기와 맞지 않았다. AVL은 n = 8,000(8.0653 ms)이 데이터가 2배인 n = 16,000(6.3009 ms)보다 오래 걸렸고, 배열도 n = 4,000 → 8,000에서 8배 넘게 늘었다. 비교 횟수와 이동 횟수는 이 구간에서도 다른 구간과 같은 비율로 늘었으므로, n = 8,000의 시간은 측정하는 순간 컴퓨터의 다른 작업 영향을 받은 것으로 판단했다. 그래서 크기 변화 분석은 실행 환경의 영향을 받지 않는 비교 횟수와 이동 횟수를 중심으로 했다.

### 5.5 삽입·삭제가 반복되는 환경에서 유리한 자료구조

**삽입·삭제가 반복되는 환경에서는 AVL 트리가 유리하다.**

| | 배열 (정렬 후 유지) | AVL 트리 |
|---|---|---|
| 정렬 | O(n log n) | O(n log n) |
| 삽입 1번 | 탐색 O(n) + 이동 O(n) | O(log n), 이동 거의 없음 |
| 삭제 1번 | 탐색 O(n) + 이동 O(n) | O(log n), 이동 거의 없음 |
| k번 삽입·삭제 | O(k × n) | O(k × log n) |
| 메모리 | 값 1개당 4바이트 | 값 1개당 32바이트 |

- 이번 실험에서 연산이 n의 20%밖에 되지 않았는데도, n = 20,000에서 배열은 AVL보다 비교가 약 89배, 이동이 약 1,279배 많았고, 시간은 약 20.7배 오래 걸렸다. 연산 횟수가 많아지고 n이 커질수록 이 차이는 더 커진다.
- 이유는 구조의 차이다. 배열은 값이 메모리에 순서대로 붙어 있어야 해서 중간에 넣고 빼려면 뒤의 값을 모두 옮겨야 하고, 이번 구현처럼 선형 탐색을 쓰면 위치를 찾는 데도 O(n)이 걸린다. AVL 트리는 포인터로 연결되어 있어서 포인터만 바꾸면 되고, 회전으로 높이를 log n으로 유지하기 때문에 찾는 것도 빠르다.
- 반대로 배열이 유리한 경우도 있다. 데이터를 한 번 정렬한 뒤 삽입·삭제 없이 읽기만 하거나, 메모리가 부족한 경우다. 이번 실험에서도 배열의 메모리는 AVL의 약 1/7이었고, 정렬 단계의 비교 횟수만 보면 퀵 정렬이 오히려 약 9 ~ 15% 적었다.

### 5.6 결론
- **정렬만** 할 때는 퀵 정렬과 AVL 트리 정렬의 비교 횟수가 비슷했다(둘 다 O(n log n)).
- **삽입·삭제가 반복되면** 배열은 연산 1번마다 O(n)의 탐색과 이동이 필요해서, 전체 비용이 n²에 비례해 늘었다. AVL 트리는 연산 1번이 O(log n)이고 데이터 이동이 거의 없어서, 비교·이동·시간 모두 크게 앞섰다.
- **메모리**는 AVL 트리가 노드마다 포인터와 높이를 저장해야 해서 배열의 약 7배를 사용했다.
- 따라서 데이터가 자주 바뀌는 환경에서는 메모리를 더 쓰더라도 **AVL 트리**가 적합하고, 데이터가 거의 바뀌지 않거나 메모리가 부족한 환경에서는 **정렬된 배열**이 적합하다고 판단했다.
