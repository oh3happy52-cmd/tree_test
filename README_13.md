# 과제 13: 병합 정렬과 퀵 정렬의 성능 비교

## 1. 실행 환경


- 실행할 때마다 `srand(time(NULL))`로 새로운 무작위 데이터를 만들기 때문에 결과는 실행마다 조금씩 달라진다.

## 2. 구현 내용

### 2.1 데이터 생성
- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 과제 12와 같은 방법으로 0 ~ 99,999 범위의 무작위 정수를 만들었고, 중복 값도 허용했다.
- 각 크기마다 원본 배열을 하나 만들고, 4가지 정렬은 모두 `memcpy()`로 복사한 배열을 정렬했다. 따라서 4가지 정렬은 완전히 같은 데이터를 정렬한다.
- 정렬이 끝날 때마다 `is_sorted()`로 오름차순 정렬이 맞는지 확인했고, 모든 경우에 정렬 오류는 없었다.

### 2.2 병합 정렬
- `merge_sort_rec()`가 구간을 가운데에서 반으로 나누고, 왼쪽 절반과 오른쪽 절반을 각각 재귀 호출로 정렬한다.
- `merge()`가 정렬된 두 부분의 맨 앞 값끼리 비교해서 작은 값부터 임시 배열 `sorted`에 넣는다. 한쪽이 먼저 비면 남은 값은 비교 없이 그대로 붙인다. 마지막에 임시 배열의 결과를 원래 배열로 다시 복사한다.
- 두 값이 같으면 왼쪽 값을 먼저 넣도록 `<=`로 비교해서 안정 정렬이 되게 했다.
- 임시 배열은 `merge_sort()`에서 크기 n으로 한 번만 할당하고, 모든 병합 단계에서 같이 사용했다.

### 2.3 퀵 정렬
- 과제 12에서 구현한 퀵 정렬을 그대로 사용했다.
- 피벗 선택 방법만 First / Random / Median-of-Three로 다르고, 선택한 피벗을 구간 첫 칸으로 옮긴 뒤 같은 `partition()` 함수로 분할한다.

## 3. 측정 방법

### 3.1 숫자 비교 횟수
- 데이터 값끼리 비교할 때는 `LESS()`, `GREATER()`, `LESS_EQUAL()` 함수만 사용했고, 이 함수가 호출될 때마다 `cmp_count`를 1씩 늘렸다.
- 병합 정렬: `merge()`에서 두 부분의 맨 앞 값을 비교한 횟수
- 퀵 정렬: 분할 과정에서 데이터 값과 피벗을 비교한 횟수 + Median-of-Three에서 중앙값을 정하는 비교 횟수
- 반복문의 인덱스 비교, 종료 조건 검사, 무작위 위치 생성, 데이터 이동은 포함하지 않았다.

### 3.2 실행시간
- C11 표준 함수 `timespec_get()`으로 정렬 함수를 호출하기 직전과 끝난 직후의 시간을 재서 그 차이를 ms 단위로 계산했다.
- 실행시간이 매우 짧아서, 같은 데이터를 10번 정렬하고 평균을 냈다.
- 데이터 생성, 배열 복사, 정렬 확인, 결과 출력은 측정 구간 밖에서 했다.
- 4가지 정렬 모두 같은 측정 방법과 단위(ms)를 사용했다.

### 3.3 메모리 사용량 (측정 방법과 계산 기준)
정렬하는 동안 필요한 **최대 추가 메모리**를 아래 두 가지의 합으로 계산했다.

**최대 추가 메모리 = 힙 메모리 + 최대 스택 사용량**

1. **힙 메모리 (직접 계산)**
   - 정렬 중에 `malloc()`으로 추가 할당한 크기를 `heap_bytes`에 직접 더했다.
   - 병합 정렬: 임시 배열 `sizeof(int) × n` = `4 × n` 바이트
   - 퀵 정렬: 추가로 할당하는 자료구조가 없어서 0 바이트
2. **최대 스택 사용량 (주소 차이로 측정)**
   - 재귀 호출이 일어날 때마다 함수의 지역 변수가 스택에 쌓이고, 스택은 높은 주소에서 낮은 주소 방향으로 자란다.
   - 정렬 함수를 부르기 직전에 지역 변수 하나의 주소를 `stack_base`로 저장했다.
   - 재귀 함수(`merge_sort_rec`, `quick_sort_rec`)와 그 안에서 부르는 함수(`merge`, `partition`, `median_of_three`)가 시작될 때마다 지역 변수의 주소를 확인해서, 가장 낮은 주소를 `stack_min`에 저장했다.
   - `stack_base - stack_min`이 정렬 중 스택이 가장 깊이 쌓였을 때의 크기다.
   - 값 하나를 비교하는 `LESS()` 같은 아주 작은 함수의 스택은 포함하지 않았기 때문에 실제보다 수십 바이트 정도 작게 측정될 수 있다.
3. **제외한 것**
   - 원본 데이터 배열과 복사본 배열은 모든 정렬에 공통인 비용이라서 제외했다.

메모리와 비교 횟수는 측정용 코드가 실행시간에 영향을 주지 않도록, 실행시간 측정과 따로 첫 번째 정렬에서 측정했다. 출력 마지막의 `[Memory Detail]` 표에 힙, 스택, 최대 재귀 깊이를 나누어 출력했다.

## 5. 분석

### 5.1 데이터 크기 증가에 따른 비교 횟수 변화

**두 정렬 모두 O(n log n)으로 증가했다.**
n이 2배가 될 때 비교 횟수의 증가 비율을 계산했다.

| n 변화 | Merge Sort | Quick (Median3) | n log₂n |
|---|---:|---:|---:|
| 1,000 → 2,000 | 2.23배 | 2.10배 | 2.20배 |
| 2,000 → 4,000 | 2.21배 | 2.31배 | 2.18배 |
| 4,000 → 8,000 | 2.19배 | 2.07배 | 2.17배 |
| 8,000 → 16,000 | 2.17배 | 2.22배 | 2.15배 |

두 정렬 모두 n이 2배가 되면 비교 횟수가 약 2.1~2.3배로 늘었고, 이는 n log₂n의 증가 비율과 거의 같았다. 특히 병합 정렬은 증가 비율이 n log₂n과 거의 똑같았고, 퀵 정렬은 피벗에 따라 분할 결과가 달라져서 비율이 조금 들쭉날쭉했다.

**병합 정렬이 퀵 정렬보다 비교 횟수가 약 26~30% 적었다.**
비교 횟수를 n log₂n으로 나누면 병합 정렬은 약 0.87~0.91, 퀵 정렬은 약 1.15~1.35였다.

- 병합 정렬은 항상 구간을 **정확히 반으로** 나눈다. 그래서 데이터와 상관없이 단계 수가 log₂n으로 일정하다. 또 병합할 때 한쪽 부분이 먼저 비면 나머지 값은 비교 없이 붙이기 때문에, 비교 횟수가 n log₂n보다 적다. 실제로 병합 정렬의 비교 횟수는 n log₂n − 1.25n(n = 1,000에서 8,716, n = 20,000에서 260,754)과 거의 같았다.
- 퀵 정렬은 피벗이 구간을 정확히 반으로 나누지 못하는 경우가 많아서, 단계 수가 log₂n보다 많아진다. 또 분할할 때 `low`와 `high`가 엇갈리는 지점 근처에서 같은 값을 두 번 비교하는 경우도 있어서 비교 횟수가 더 많다.

### 5.2 실행시간 차이

**비교 횟수는 병합 정렬이 적었지만, 실행시간은 두 정렬이 비슷했다.**
6가지 크기 중 n = 2,000에서만 병합 정렬이 가장 빨랐고, 나머지 5가지 크기에서는 Quick(First)나 Quick(Median3)가 가장 빨랐다. 가장 빠른 퀵 정렬과 병합 정렬의 차이는 약 4~12%로 크지 않았다.

비교 1번당 걸린 시간을 계산해 보면 이유를 알 수 있다.

| | 비교 1번당 시간 |
|---|---:|
| Merge Sort | 약 15~16 ns |
| Quick Sort | 약 11~12 ns |

병합 정렬은 비교 1번마다 할 일이 더 많았다.
- 병합 정렬은 값을 임시 배열에 넣고, 병합이 끝나면 **원래 배열로 다시 복사**한다. 즉 모든 단계에서 데이터를 두 번씩 옮긴다.
- 퀵 정렬은 원래 배열 안에서 필요한 두 값만 교환하는 **제자리 정렬**이라서, 데이터 이동이 적다.

그래서 병합 정렬은 비교 횟수가 약 28% 적은 이점이 있었지만, 데이터 이동 비용이 커서 실행시간에서는 그 이점이 거의 없어졌다.

또한 이번 프로그램은 비교할 때마다 비교 횟수를 세는 함수를 호출한다. 이 함수 호출 시간은 비교 횟수에 비례하므로, 비교 횟수가 적은 병합 정렬에 조금 유리하게 작용했다고 생각했다. 비교 횟수를 세지 않는 실제 프로그램이었다면 퀵 정렬이 더 확실하게 빨랐을 것이다.

n = 16,000에서 Quick(First)의 시간이 n = 20,000보다 오히려 길게 나온 것처럼, 일부 결과는 측정 순간의 컴퓨터 상태 영향을 받았다. 10번 평균을 냈지만 1ms 단위의 짧은 시간이라 이런 오차가 생긴 것으로 판단했다.

### 5.3 메모리 사용량 차이

**병합 정렬은 n에 비례해서 늘어났고, 퀵 정렬은 거의 늘어나지 않았다.**
n이 1,000에서 20,000으로 20배가 될 때, 병합 정렬은 4,852B에서 81,172B로 약 17배 늘었고, 퀵 정렬(Median3)은 1,348B에서 1,988B로 약 1.5배만 늘었다.

- **병합 정렬**: 병합할 때 결과를 담을 임시 배열이 필요하다. 임시 배열 크기가 `4 × n` 바이트라서, n = 20,000일 때 전체 추가 메모리 81,172B 중 80,000B(약 99%)가 임시 배열이었다. 재귀 스택은 1,172B로 작았다.
- **퀵 정렬**: 원래 배열 안에서 교환만 하므로 임시 배열이 필요 없다. 추가 메모리는 재귀 호출 스택뿐이다.

**재귀 스택은 재귀 깊이에 비례했다.**
- 병합 정렬의 최대 재귀 깊이는 11, 12, 13, 14, 15, 16으로, n이 2배가 될 때마다 정확히 1씩 늘었다. 항상 반으로 나누기 때문에 깊이가 ⌈log₂n⌉ + 1로 정해져 있다.
- 깊이가 1 늘 때마다 병합 정렬의 스택은 정확히 64B씩 늘었다(852 → 916 → 980 ...). 즉 이 환경에서 재귀 함수 한 번의 스택 크기는 약 64B다.
- 퀵 정렬의 재귀 깊이는 n = 20,000에서 29~35로 병합 정렬(16)의 약 2배였다. 피벗이 구간을 반반으로 나누지 못해서 한쪽 구간이 더 길게 남기 때문이다. 그래서 스택만 비교하면 오히려 퀵 정렬이 더 많이 썼다. 하지만 병합 정렬은 임시 배열이 훨씬 크기 때문에, 전체 추가 메모리는 퀵 정렬이 훨씬 적었다.

### 5.4 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **비교 횟수**: n = 2,000 ~ 16,000에서는 Median3가 세 방법 중 가장 적었다. 특히 n = 16,000에서는 First보다 약 10% 적었다. n = 1,000에서는 First, n = 20,000에서는 Random이 가장 적었는데, 과제 12에서 확인했듯이 무작위 데이터에서는 한 번의 실행 결과에 우연이 많이 섞인다.
- **재귀 깊이와 메모리**: Median3의 재귀 깊이는 17~29로, First(19~35)와 Random(23~33)보다 대체로 얕았다. 세 값 중 가운데 값을 피벗으로 쓰면 구간이 더 고르게 나뉘기 때문이다. 그래서 스택 메모리도 Median3가 n = 2,000 이상에서 가장 적었다.
- **실행시간**: Random은 n = 1,000 ~ 8,000에서 세 퀵 정렬 중 가장 느렸다. 분할할 때마다 난수를 만드는 비용이 추가되기 때문이다. Median3는 중앙값을 구하는 비교가 2~3번 더 들어가지만, 분할이 고르게 되어 전체 비교 횟수와 깊이가 줄어서 First와 비슷하거나 더 빨랐다.
- **First와 Random이 비슷한 이유**: 데이터가 무작위라서 첫 번째 원소도 사실상 무작위로 뽑은 값과 같기 때문이다. 하지만 이미 정렬된 데이터라면 First는 매번 가장 작은 값을 피벗으로 골라서 O(n²)이 되고 재귀 깊이도 n까지 깊어진다. 따라서 실제로 쓰기에는 Median3가 가장 안정적이라고 판단했다.

### 5.5 시간 복잡도와 공간 복잡도 차이

| | 병합 정렬 | 퀵 정렬 |
|---|---|---|
| 최선 시간 | O(n log n) | O(n log n) |
| 평균 시간 | O(n log n) | O(n log n) |
| 최악 시간 | O(n log n) | O(n²) |
| 추가 메모리 | O(n) 임시 배열 + O(log n) 스택 | 평균 O(log n) 스택, 최악 O(n) |
| 안정 정렬 | O | X |

- **시간 복잡도**: 병합 정렬은 데이터 상태와 상관없이 항상 반으로 나누기 때문에 최악에도 O(n log n)이다. 실험에서도 비교 횟수가 n log₂n − 1.25n과 거의 같게 일정하게 나왔다. 퀵 정렬은 평균 O(n log n)이지만, 피벗이 계속 한쪽 끝 값이면 O(n²)이 된다. 실험에서 퀵 정렬의 비교 횟수가 피벗 방법과 실행마다 들쭉날쭉했던 것도 이 때문이다.
- **공간 복잡도**: 병합 정렬은 임시 배열 때문에 O(n)이고, 실험에서도 메모리가 n에 정비례(4 × n + 약 1KB)했다. 퀵 정렬은 재귀 스택만 쓰므로 평균 O(log n)이고, 실험에서도 n이 20배가 되는 동안 메모리는 1.5배 정도만 늘었다.

### 5.6 결론
- **비교 횟수**는 병합 정렬이 약 26~30% 적었다. 항상 정확히 반으로 나누기 때문이다.
- **실행시간**은 두 정렬이 비슷했고, 대부분의 크기에서 퀵 정렬(First, Median3)이 조금 빨랐다. 병합 정렬은 임시 배열로 데이터를 옮기고 다시 복사하는 비용이 커서 비교 횟수의 이점이 상쇄되었다.
- **메모리**는 퀵 정렬이 훨씬 적었다. n = 20,000에서 병합 정렬은 81,172B, 퀵 정렬은 약 2,000B였다.
- 메모리가 중요하고 평균 속도가 중요하면 **퀵 정렬(Median-of-Three)** 이 적합하고, 최악의 경우에도 성능이 보장되어야 하거나 안정 정렬이 필요하면 **병합 정렬**이 적합하다고 판단했다.
