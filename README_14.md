# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 실행 방법

- 실행할 때마다 `srand(time(NULL))`로 새로운 무작위 데이터를 만들기 때문에 결과는 실행마다 조금씩 달라진다. 그래서 프로그램을 3번 실행했다.

## 2. 구현 내용

### 2.1 데이터 생성
- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 이전 과제와 같은 방법으로 0 ~ 99,999 범위의 무작위 정수를 만들었고, 중복 값도 허용했다.
- 각 크기마다 원본 배열을 하나 만들고, 5가지 정렬은 모두 `memcpy()`로 복사한 배열을 정렬했다. 따라서 5가지 정렬은 완전히 같은 데이터를 정렬한다.
- 정렬이 끝날 때마다 `is_sorted()`로 오름차순 정렬이 맞는지 확인했고, 모든 경우에 정렬 오류는 없었다.

### 2.2 힙 정렬
- **입력 배열 자체를 최대 힙으로 사용**했고, 별도의 힙 저장 배열은 만들지 않았다. 0번 칸이 루트이고, i번 칸의 자식은 (2i+1)번, (2i+2)번 칸이다.
- **최대 힙 구성**: 마지막 부모 칸(n/2 − 1번)부터 0번 칸까지 거꾸로 가면서 `heapify()`를 실행했다.
- **정렬**: 루트(0번 칸)의 최댓값을 힙의 마지막 칸과 교환하고, 힙 크기를 1 줄인 다음 0번 칸에서 `heapify()`로 힙 속성을 복구했다. 이것을 힙 크기가 1이 될 때까지 반복했다.
- **`heapify()`**: 현재 칸에서 시작해서 아래로 내려가며 다음 두 비교를 반복한다.
  1. 왼쪽 자식과 오른쪽 자식을 비교해서 더 큰 자식을 고른다.
  2. 부모와 더 큰 자식을 비교해서, 부모가 작으면 교환하고 한 칸 아래로 내려간다. 부모가 크거나 같으면 멈춘다.
- `heapify()`는 재귀가 아니라 `while` 반복문으로 구현했다.

### 2.3 병합 정렬과 퀵 정렬
- 병합 정렬은 과제 13에서 구현한 것을 그대로 사용했다. 크기 n인 임시 배열을 한 번 할당하고, 구간을 반으로 나눠 재귀로 정렬한 뒤 병합한다.
- 퀵 정렬은 과제 12, 13에서 구현한 것을 그대로 사용했다. First / Random / Median-of-Three는 피벗을 고르는 부분만 다르고, 같은 `partition()` 함수로 분할한다.

## 3. 측정 방법

### 3.1 숫자 비교 횟수
- 데이터 값끼리 비교할 때는 `LESS()`, `GREATER()`, `LESS_EQUAL()` 함수만 사용했고, 이 함수가 호출될 때마다 `cmp_count`를 1씩 늘렸다.
- 힙 정렬: 힙 구성 과정과 힙 속성 복구 과정의 `heapify()`에서 자식끼리 비교한 횟수 + 부모와 자식을 비교한 횟수
- 병합 정렬: `merge()`에서 두 부분의 맨 앞 값을 비교한 횟수
- 퀵 정렬: 분할 과정에서 데이터 값과 피벗을 비교한 횟수 + Median-of-Three에서 중앙값을 정하는 비교 횟수
- 자식이 있는지 확인하는 인덱스 비교, 반복문의 종료 조건 검사, 무작위 위치 생성, 데이터 이동은 포함하지 않았다.

### 3.2 실행시간
- C11 표준 함수 `timespec_get()`으로 정렬 함수를 호출하기 직전과 끝난 직후의 시간을 재서 그 차이를 ms 단위로 계산했다.
- 실행시간이 매우 짧아서, 같은 데이터를 10번 정렬하고 평균을 냈다.
- 데이터 생성, 배열 복사, 정렬 확인, 결과 출력은 측정 구간 밖에서 했다.
- 5가지 정렬 모두 같은 측정 방법과 단위(ms)를 사용했다.

### 3.3 메모리 사용량 (측정 방법과 계산 기준)
정렬하는 동안 필요한 **최대 추가 메모리**를 아래 두 가지의 합으로 계산했다.

**최대 추가 메모리 = malloc 메모리 + 최대 스택 사용량**

1. **malloc 메모리 (직접 계산)**
   - 정렬 중에 `malloc()`으로 추가 할당한 크기를 직접 더했다.
   - 병합 정렬: 임시 배열 `sizeof(int) × n` = `4 × n` 바이트
   - 힙 정렬, 퀵 정렬: 추가로 할당하는 배열이 없어서 0 바이트
   - 출력에서 힙 정렬의 "힙"과 헷갈리지 않도록 이 항목의 이름을 `Malloc(B)`로 표시했다.
2. **최대 스택 사용량 (주소 차이로 측정)**
   - 함수가 호출되면 그 함수의 지역 변수(보조 변수)가 스택에 쌓이고, 스택은 높은 주소에서 낮은 주소 방향으로 자란다.
   - 정렬 함수를 부르기 직전에 지역 변수 하나의 주소를 `stack_base`로 저장했다.
   - 정렬 함수와 그 안에서 부르는 함수(`heap_sort`, `heapify`, `merge_sort_rec`, `merge`, `quick_sort_rec`, `partition`, `median_of_three`)가 시작될 때마다 지역 변수의 주소를 확인해서, 가장 낮은 주소를 `stack_min`에 저장했다.
   - `stack_base - stack_min`이 정렬 중 스택이 가장 깊이 쌓였을 때의 크기다. 힙 정렬의 보조 변수(`i`, `left`, `right`, `child` 등)와 병합·퀵 정렬의 재귀 호출 스택이 모두 여기에 들어간다.
   - 값 하나를 비교하는 `LESS()` 같은 아주 작은 함수의 스택은 포함하지 않았기 때문에 실제보다 수십 바이트 정도 작게 측정될 수 있다.
3. **제외한 것**
   - 원본 데이터 배열과 복사본 배열은 모든 정렬에 공통인 비용이라서 제외했다.

비교 횟수와 메모리는 측정용 코드가 실행시간에 영향을 주지 않도록, 실행시간 측정과 따로 첫 번째 정렬에서 측정했다. 출력 마지막의 `[Memory Detail]` 표에 malloc 메모리, 스택, 최대 재귀 깊이를 나누어 출력했다.

### 3.4 실행시간 결과를 고른 기준
3번 실행한 결과 중 실행시간은 **3회차 결과를 대표값으로 사용**했다.

- **1회차**: 실행할 때 MySQL 서버와 Docker가 백그라운드에서 CPU를 쓰고 있었다(활성 상태 보기에서 `mysqld` 약 33%, Docker 약 17%). 같은 병합 정렬 코드가 과제 13(n = 20,000에서 4.2637 ms)보다 약 4배 느린 16.8712 ms로 나왔고, n = 4,000의 Quick(Median3)가 3.1390 ms인데 5배 큰 n = 20,000은 6.3955 ms로 크기와 시간이 맞지 않았다. 그래서 1회차의 실행시간은 분석에서 제외했다.
- **2회차**: MySQL과 Docker를 정리한 뒤 실행했지만, n = 20,000의 병합 정렬이 8.8440 ms로 3회차(4.0211 ms)의 2배가 넘는 등 일부 값이 튀었다.
- **3회차**: 모든 알고리즘의 시간이 데이터 크기에 맞게 일정한 비율로 늘었고, 과제 13의 결과와도 비슷했다.

비교 횟수와 메모리는 실행 환경의 영향을 받지 않기 때문에 3번의 결과를 모두 사용했다.

## 5. 분석

### 5.1 데이터 크기 증가에 따른 비교 횟수 변화

**세 정렬 모두 O(n log n)으로 증가했다.**
n이 2배가 될 때 비교 횟수(3회 평균)의 증가 비율을 계산했다.

| n 변화 | Heap Sort | Merge Sort | Quick (Median3) | n log₂n |
|---|---:|---:|---:|---:|
| 1,000 → 2,000 | 2.23배 | 2.23배 | 2.23배 | 2.20배 |
| 2,000 → 4,000 | 2.21배 | 2.21배 | 2.13배 | 2.18배 |
| 4,000 → 8,000 | 2.19배 | 2.19배 | 2.23배 | 2.17배 |
| 8,000 → 16,000 | 2.17배 | 2.17배 | 2.15배 | 2.15배 |

세 정렬 모두 n이 2배가 되면 비교 횟수가 약 2.1~2.2배로 늘었고, n log₂n의 증가 비율과 거의 같았다. 힙 정렬과 병합 정렬은 증가 비율이 n log₂n과 거의 똑같았고, 퀵 정렬은 피벗에 따라 분할 결과가 달라서 조금 들쭉날쭉했다.

**하지만 같은 O(n log n)이라도 앞에 붙는 상수가 달랐다.**
비교 횟수를 n log₂n으로 나눈 값은 다음과 같았다.

| | 비교 횟수 ÷ n log₂n |
|---|---:|
| Heap Sort | 1.69 ~ 1.79 |
| Merge Sort | 0.87 ~ 0.91 |
| Quick Sort | 1.17 ~ 1.31 |

그래서 비교 횟수는 **병합 정렬 < 퀵 정렬 < 힙 정렬** 순서였다. 힙 정렬은 병합 정렬의 약 1.94~1.96배, 퀵 정렬(세 방법 평균)은 병합 정렬의 약 1.33~1.40배였다.

- **힙 정렬이 가장 많은 이유**: `heapify()`는 한 단계 내려갈 때마다 비교를 2번 한다(자식끼리 1번, 부모와 큰 자식 1번). 또 정렬 단계에서는 힙의 마지막 칸 값, 즉 힙 아래쪽에 있던 작은 값이 루트로 올라온다. 이 작은 값은 거의 항상 맨 아래까지 다시 내려가야 해서, 한 번 꺼낼 때마다 약 log₂n 단계 × 2번의 비교가 생긴다. 그래서 전체 비교 횟수가 약 2n log₂n에 가까워진다. 실제로 n log₂n으로 나눈 값이 1.69에서 1.79로 n이 커질수록 2에 가까워졌다.
- **병합 정렬이 가장 적은 이유**: 항상 정확히 반으로 나누기 때문에 단계 수가 log₂n으로 일정하고, 병합 중 한쪽이 먼저 비면 남은 값은 비교 없이 붙인다. 그래서 비교 횟수가 n log₂n보다 적다.
- **퀵 정렬이 중간인 이유**: 피벗이 구간을 정확히 반으로 나누지 못하면 단계 수가 늘어나서 병합 정렬보다 많다. 하지만 분할할 때 값마다 피벗과 거의 한 번씩만 비교하기 때문에 힙 정렬보다는 적다.

또 힙 정렬과 병합 정렬은 3번 실행한 비교 횟수의 차이가 매우 작았다(n = 20,000에서 힙 정렬 510,615 ~ 510,855). 데이터가 달라도 나누는 방법(힙의 모양, 반으로 나누기)이 정해져 있기 때문이다. 반면 퀵 정렬은 피벗에 따라 분할이 달라져서 같은 크기에서도 실행마다 차이가 컸다(n = 20,000의 First: 351,838 ~ 370,269).

### 5.2 실행시간 차이

**실행시간은 퀵 정렬 ≤ 병합 정렬 < 힙 정렬 순서였다.**
3회차 결과에서 힙 정렬은 6가지 크기 모두에서 가장 느렸다. 가장 빠른 것은 Quick(First)(5가지 크기)와 Quick(Median3)(n = 2,000)였다. n = 20,000에서 힙 정렬은 Quick(First)보다 약 1.31배, 병합 정렬보다 약 1.24배 오래 걸렸다.

비교 1번당 걸린 시간을 계산하면 각 정렬의 특징이 보인다(3회차 기준).

| | 비교 1번당 시간 |
|---|---:|
| Heap Sort | 약 9.7 ~ 10.4 ns |
| Merge Sort | 약 15.4 ~ 15.7 ns |
| Quick Sort | 약 10.6 ~ 14.2 ns |

- **힙 정렬**: 비교 1번당 시간은 가장 짧았다. `heapify()`는 비교하고 필요하면 두 값을 교환하는 단순한 작업만 반복하기 때문이다. 하지만 비교 횟수가 병합 정렬의 약 2배라서 전체 시간은 가장 길었다. 즉 힙 정렬이 느린 가장 큰 이유는 비교 횟수다.
- **병합 정렬**: 비교 횟수는 가장 적지만 비교 1번당 시간이 가장 길었다. 값을 임시 배열에 넣고, 병합이 끝나면 원래 배열로 다시 복사하기 때문에 모든 단계에서 데이터를 두 번씩 옮긴다. 그래서 비교 횟수의 이점이 줄어들어 퀵 정렬과 비슷하거나 조금 느렸다.
- **퀵 정렬**: 비교 횟수는 중간이고, 원래 배열 안에서 필요한 두 값만 교환하는 제자리 정렬이라 데이터 이동이 적다. 두 가지가 균형을 이뤄서 가장 빨랐다.

또한 이번 프로그램은 비교할 때마다 비교 횟수를 세는 함수를 호출한다. 이 시간은 비교 횟수에 비례하므로 비교가 많은 힙 정렬에 더 불리하게 작용했다.

힙 정렬의 실행시간도 n이 2배가 될 때 약 2.08~2.27배로 늘어서, 실행시간에서도 O(n log n)을 확인할 수 있었다.

### 5.3 메모리 사용량 차이

**메모리는 힙 정렬 < 퀵 정렬 < 병합 정렬 순서였다.**

- **힙 정렬 (184B, n과 상관없이 일정)**: 입력 배열 자체를 힙으로 쓰기 때문에 추가 배열이 필요 없다. 또 `heapify()`를 반복문으로 구현해서 재귀 호출이 없다. 그래서 필요한 메모리는 `heap_sort()`와 `heapify()` 함수 하나씩의 보조 변수(`i`, `left`, `right`, `child` 등)뿐이고, n이 1,000이든 20,000이든 184B로 똑같았다.
- **퀵 정렬 (약 1.2~2.3KB, 천천히 증가)**: 추가 배열은 없지만 재귀 호출 스택이 필요하다. 재귀 깊이가 n = 20,000에서 25~33으로, 깊이가 깊을수록 스택이 커졌다. n이 20배가 되는 동안 메모리는 약 1.5배만 늘었다.
- **병합 정렬 (약 4.8~81KB, n에 비례)**: 병합할 때 결과를 담을 임시 배열(4 × n 바이트)이 필요하다. n = 20,000에서 전체 81,172B 중 80,000B(약 99%)가 임시 배열이었다. 재귀 깊이는 16으로 퀵 정렬보다 얕았지만, 임시 배열 때문에 메모리가 가장 많았다.

n = 20,000에서 병합 정렬은 힙 정렬보다 약 441배 많은 메모리를 사용했다.

### 5.4 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **비교 횟수**: 3회 평균에서 Median3가 6가지 크기 모두에서 가장 적었다. n = 20,000에서 First보다 약 7%, Random보다 약 4% 적었다. 세 값 중 가운데 값을 피벗으로 쓰면 피벗이 구간의 가운데 크기에 가까워져서, 구간이 더 고르게 나뉘기 때문이다.
- **재귀 깊이와 메모리**: Median3의 재귀 깊이가 가장 얕았다(3회차 n = 20,000에서 Median3 25, Random 31, First 33). 그래서 3회차 기준으로 모든 크기에서 Median3의 메모리가 가장 적었다.
- **실행시간**: Random은 3회차의 6가지 크기 모두에서 세 퀵 정렬 중 가장 느렸다. 분할할 때마다 난수를 만드는 비용이 더해지기 때문이다. First와 Median3는 차이가 0.002~0.12 ms로 거의 같았다. Median3는 중앙값을 구하는 비교가 2~3번 더 들어가지만, 분할이 고르게 되어 줄어드는 비교와 비슷하게 상쇄되었다.
- **First와 Random이 비슷한 이유**: 데이터가 무작위라서 첫 번째 원소도 사실상 무작위로 뽑은 값과 같기 때문이다. 하지만 이미 정렬된 데이터라면 First는 매번 가장 작은 값을 피벗으로 골라서 O(n²)이 되고, 재귀 깊이도 n까지 깊어진다. 그래서 실제로 쓰기에는 Median3가 가장 안정적이라고 판단했다.

### 5.5 시간 복잡도와 공간 복잡도 비교

| | 힙 정렬 | 병합 정렬 | 퀵 정렬 |
|---|---|---|---|
| 최선 시간 | O(n log n) | O(n log n) | O(n log n) |
| 평균 시간 | O(n log n) | O(n log n) | O(n log n) |
| 최악 시간 | O(n log n) | O(n log n) | O(n²) |
| 추가 메모리 | O(1) | O(n) 임시 배열 + O(log n) 스택 | 평균 O(log n), 최악 O(n) 스택 |
| 안정 정렬 | X | O | X |
| 실험 비교 횟수 | 약 1.7~1.8 n log₂n | 약 0.9 n log₂n | 약 1.2~1.3 n log₂n |
| 실험 메모리 (n = 20,000) | 184B | 81,172B | 1,732 ~ 2,196B |

- **시간 복잡도**: 힙 정렬과 병합 정렬은 데이터 상태와 상관없이 최악에도 O(n log n)이다. 실험에서도 두 정렬의 비교 횟수는 실행마다 거의 같았다. 퀵 정렬은 평균 O(n log n)이지만 피벗이 계속 한쪽 끝 값이면 O(n²)이 된다.
- **공간 복잡도**: 힙 정렬은 O(1)이고, 실험에서도 n과 상관없이 184B로 일정했다. 퀵 정렬은 평균 O(log n)으로 천천히 늘었고, 병합 정렬은 O(n)으로 n에 정비례했다.

### 5.6 결론
- **비교 횟수**: 병합 정렬이 가장 적고, 힙 정렬이 가장 많았다(병합 정렬의 약 2배). 힙 정렬은 작은 값을 루트에서 맨 아래까지 매번 다시 내려보내고, 한 단계마다 비교를 2번 하기 때문이다.
- **실행시간**: 퀵 정렬이 가장 빨랐고, 힙 정렬이 가장 느렸다. 병합 정렬은 비교는 적지만 데이터 복사 비용 때문에 퀵 정렬보다 조금 느렸다.
- **메모리**: 힙 정렬이 가장 적었다(184B, 일정). 병합 정렬은 임시 배열 때문에 가장 많았다(n = 20,000에서 81,172B).
- 평균 속도가 가장 중요하면 **퀵 정렬(Median-of-Three)**, 메모리가 부족하면서 최악의 경우에도 O(n log n)이 보장되어야 하면 **힙 정렬**, 안정 정렬이 필요하거나 최악의 경우 성능이 중요하고 메모리 여유가 있으면 **병합 정렬**이 적합하다고 판단했다.
